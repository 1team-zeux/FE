# ZeuX 프로젝트 기획서 v5

> **용도**: ChatGPT, Claude, Codex 등 AI 도구에게 프로젝트 맥락을 빠르게 전달하기 위한 기준 문서
> **작성 기준**: 2026-05-11 현재 프로젝트 방향, 교수님 피드백, 최신 시스템 구성도 v3 반영
> **프로젝트명**: ZeuX
> **큰 주제**: B2B 클라우드 인프라 운영 AX 솔루션
> **핵심 한 줄**: SK AX 클라우드 서비스 운영팀이 더 많은 고객사 인프라를 안정적으로 관리하도록, 인프라 구축·모니터링·장애 대응 업무를 Multi-Agent가 보조·자동화하는 Cloud Infra AIOps 서비스

## 0. 방향성 원칙

### 핵심 프레이밍

- ZeuX는 **운영자를 없애는 서비스가 아님**
- ZeuX는 **운영자의 업무 범위와 처리량을 확장하는 서비스**
- 목표는 사람을 대체하는 것이 아니라, 사람이 직접 하던 반복 작업을 Agent가 처리하고 운영자는 감독·승인·예외 대응에 집중하는 구조

### 발표/문서에서 사용할 표현

- ❌ 운영 인력을 대체한다
- ✅ 운영 인력의 업무 효율을 높인다
- ✅ 10명이 10개를 관리하던 업무를 100개를 관리하는 효율적인 구조로 전환한다
- ✅ 운영자는 실행자에서 감독자로 이동한다
- ✅ AI Agent가 반복 구축·관제·분석·초기 조치를 보조한다

### HITL 원칙 (Human-in-the-Loop)

- ZeuX의 AI 자율 동작은 모든 주요 단계에서 HITL을 거친다.
- 흐름은 항상 다음과 같다.
  AI가 안을 만든다 → 운영자가 검토·승인한다 → 그 후에 실행된다.
- Self-healing 같은 자율 동작도 사전 승인된 정책 범위 내에서만 발동된다.
- HITL은 0번 방향성의 "실행자 → 감독자" 이동을 실제 시스템에서 구현하는 메커니즘이다.
- 동시에 HITL 흐름 자체가 운영 의사결정의 감사 추적 자산이 된다.

### SLA 표현 원칙

- SLA는 ZeuX의 가치 측정 단위이자 Agent 의사결정의 기준이다.
- ZeuX는 SLA, SLI, Error Budget 세 개념을 사용한다.
  - SLA: 외부 고객사와 SK AX 간 계약상 약속.
    예: 가용성 99.9%, 응답시간, 장애 건수.
    → SK AX 사업 책임자(주연 2)와 외부 고객사 SLA Owner(조연 1)의 관심사.
  - SLI: 서비스 상태를 실시간으로 나타내는 측정값.
    예: 현재 응답 성공률, 현재 P99 응답시간.
    → Agent가 항상 관찰하는 신호.
  - Error Budget: SLA에서 직접 파생되는 허용 가능한 실패량.
    예: SLA 99.9%면 0.1%가 한 달 Error Budget.
    → Agent의 자동 조치 트리거이자 위반 사전 예측의 정량 기준.
- 의사결정의 흐름은 다음과 같다.
  SLI 실시간 관찰 → Error Budget 소진율 평가
  → Agent 행동 결정 → SLA 위반 전 회복.
- SRE 표준의 SLO는 MVP 범위에서 의도적으로 제외한다.
  Error Budget은 SLA에서 직접 파생되도록 단순화한다.
  (별도의 내부 목표 거버넌스를 두지 않음)
- 시연에서는 세 개념이 함께 작동하는 장면을 보여준다.
  예: SLI가 SLA 임계 근접 → 남은 Error Budget 30%
  → Agent 자동 스케일아웃 → SLA 99.9%는 안전하게 보호.

## 1. Executive Summary

### What

- B2B 클라우드 인프라 운영 AX 솔루션
- SK AX 내부 클라우드 서비스 운영팀 대상
- Multi-Agent 기반으로 다음 업무를 보조·자동화
    - 신규 고객사 인프라 구축
    - IaC 코드 생성 및 검증
    - 모니터링/알람 환경 구성
    - 장애 탐지 및 원인 분석
    - 복구 방안 추천 및 일부 자동 복구
    - 운영 리포트 생성

### Why

- 고객사 수 증가 → 운영 사이트 수 증가
- 인프라 구축·관제·장애 대응 업무가 운영자에게 집중
- 알람은 많지만 실제 조치가 필요한 신호는 적음
- Datadog 등 상용 관제 도구는 사이트/호스트/컨테이너 증가에 따라 비용 부담 확대
- SI 사업에서는 운영 인력과 도구 비용이 수익성에 직접 영향

### How

- Day 0: 고객사 요구사항 → 운영 기준 해석 → 인프라 요구사항 산출 → Terraform 코드 생성 → 검토/승인(HITL) → 배포
- Day 2: Metrics/Logs/Traces 수집 → 알람 노이즈 필터링 → RCA → 조치 추천 → HITL 승인/자동 조치 → 리포트 생성
- Phase 1 (MVP)은 핵심 시연 범위, Phase 2 (확장)은 운영 고도화 범위로 구분

## 2. 문제 인식

### 2.1 클라우드 인프라 운영 환경 변화

- 클라우드 인프라 수요 지속 증가
- 기업 운영이 IT 안정화에서 AX 자율 의사결정 단계로 이동
- 인프라 운영자는 단순 서버 관리가 아니라 다음 요소를 함께 판단해야 함
    - 서비스 품질
    - 장애 가능성
    - 비용
    - 운영 기준
    - 변경 영향도

```text
IT 안정화 → DT 가시성 → AX 자율 의사결정
```

### 2.2 현재 운영의 한계

#### Pain 1. 인력 효율 정체

- 신규 고객사마다 인프라를 처음부터 수동 설계
- Terraform 코드, 모니터링 설정, 알람 룰을 반복 작성
- 고객사 수가 늘면 운영 인력도 함께 늘어나는 구조
- 표준화 가능한 업무도 운영자 경험에 의존

#### Pain 2. 운영 부담 집중

- 알람 인지 → 원인 분석 → 조치 → 보고까지 사람이 수행
- 알람 피로로 중요한 신호를 놓칠 가능성 존재
- 야간/주말 대응 부담 증가
- 장애 대응 후 보고서 작성도 수작업 반복

#### Pain 3. 외부 도구 비용 부담

- Datadog 등 상용 모니터링 도구는 강력하지만 비용 부담 큼
- 고객사/사이트/컨테이너 수 증가 시 라이선스 비용 증가
- OSS 도구를 직접 구성하려면 운영자의 설정 부담 증가
- SI 사업의 마진 구조에 부담

## 3. 이해관계자 구조

**주연 (발표·산출물에서 강조)**

| 구분 | 누구 | 받는 가치 | 메시지에서의 위치 |
|---|---|---|---|
| 주연 1 | **SK AX 클라우드 서비스 운영 담당자** (본사) | 같은 시간으로 10배 많은 사이트 감독 가능. 새벽 호출·반복 업무에서 해방. 역할이 *실행자*에서 *감독자*로 이동 | "**대체되지 않고 확장된다**" |
| 주연 2 | **SK AX 클라우드 서비스 사업 책임자** (본사) | 인력 충원 없이 수주 확장. 마진 구조 개선. SK AX의 AX 메시지를 자기 본업에 적용한 자기지시적 사례 | "**같은 인력으로 더 많은 SI 수주**" |

**조연 (산출물에 기록, 발표에선 간략 언급)**

| 구분 | 누구 | 받는 가치 | 메시지에서의 위치 |
|---|---|---|---|
| 조연 1 | 외부 고객사 SLA Owner (사업 책임자/임원) | SLA 충족·장애 감소 | "*결과적으로* 더 안정적인 서비스를 받음" |
| 조연 2 | 외부 고객사 서비스 운영팀 | 인프라 걱정 없이 비즈니스 로직에 집중 | 비즈니스 컨텍스트 정보 제공자 |
| 조연 3 | 보안·컴플라이언스 | 자율 운영의 감사 추적·권한 통제 보장 | 안전장치 검토자 |

### 3.2 이해관계자 메시지

- ZeuX의 직접 사용자는 **SK AX 본사 운영 담당자**
- 외부 고객사는 ZeuX를 직접 쓰기보다 **더 빠르고 안정적인 운영 결과**를 제공받음
- 핵심 가치는 **SK AX의 운영 역량을 AI로 확장**하는 것

## 4. 최신 시스템 구성 기준

최신 구성도는 기능을 6개 영역으로 나눈다.
나열 순서는 논리적 우선순위를 따른다: **SLA 기준 정렬 → 구축 → 운영 → 대응 → 확장**.
(시스템 구성도 다이어그램에서는 시각적 흐름에 따라 위치가 달라질 수 있으나, 본 문서의 나열 순서는 의사결정 우선순위 기준이다.)

```text
중앙 시스템 / 플랫폼 코어 (ZeuX Platform Core)
├── SLA 관리
├── IaC 인프라 구축
├── 모니터링 및 알람
├── 장애 대응(AIOps)
├── 비용 최적화
└── 용량 계획 / 예측
```

### Phase 구분

| Phase        | 범위                                                   | 목적                             |
| ------------ | ------------------------------------------------------ | -------------------------------- |
| Phase 1 (MVP) | SLA 관리, IaC 인프라 구축, 모니터링 및 알람, 장애 대응 | 구축부터 운영까지 핵심 시연 가능 |
| Phase 2 (확장) | 비용 최적화, 용량 계획/예측                            | 운영 고도화 및 사업 확장         |

### 사용자 대상

- 직접 사용자: **SK AX 본사 클라우드 서비스 운영자** (시스템 운영자, 주연 1)
- 결과 확인자: **SK AX 클라우드 서비스 사업 책임자** (주연 2)
  - 내부 계약 SLA 관점에서 운영 결과와 사이트 관리 효율을 확인
- 간접 수혜자: 외부 고객사 SLA Owner (조연 1)
  - ZeuX를 직접 사용하지 않으나 결과적으로 안정적 SLA 충족을 제공받음
- 발표·산출물의 강조 대상은 **시스템 운영자(주연 1)**

## 5. Phase 1 (MVP) 기능

## 5.1 SLA 관리

> SLA 관리는 ZeuX의 출발점이자 기준 레이어다.
> 고객사별 SLA를 입력으로 받아, Agent가 관찰할 SLI와
> 행동의 정량 기준이 될 Error Budget을 정의한다.
> IaC 구축, 모니터링, 장애 대응 등 모든 기능이 이 기준에 정렬된다.

### 기능

- SLA 번들 관리 (고객사별 SLA 묶음)
- SLI 정의/측정 (메트릭 → SLI 매핑)
- Error Budget 관리 (SLA 기반 자동 산출, 실시간 소진율 추적)
- SLA 위반 사전 예측 (Error Budget 소진 추세 기반)
- SLA 리포트 생성 (계약 SLA 충족 증빙)
- SLA Overview 대시보드 (고객사/앱 단위)
  - 상위 뷰에서 이상 신호 발견 시 → **5.3의 Service Detail 대시보드로 드릴다운**
  - 직접 사용자: 시스템 운영자(주연 1), 사업 책임자(주연 2)

### 목적

- 계약 SLA를 Agent가 이해 가능한 SLI와 Error Budget으로 변환
- 고객사별 운영 기준 표준화
- IaC 구축·모니터링·장애 대응 전 기능이 동일한 SLA 기준 참조
- 운영자가 고객사/앱별 SLA 충족 상태와 남은 Error Budget을 한눈에 확인

---

## 5.2 IaC 인프라 구축

### 기능

- IaC 코드 생성 (AI)
- 배포 전략 추천 (AI)
- 배포안 검토/승인 (HITL)
- IaC 배포 실행
- 배포 안정성 검증
- IaC Drift 감지 (일관성 모니터링)
  - 배포 이후 운영 중 지속 동작
  - 다른 박스들이 신규 배포의 한 단계인 반면, Drift 감지는 운영 시점의 지속 감시

### 목적

- 신규 고객사마다 반복되는 인프라 설계·코드 작성 부담 감소
- Terraform 기반 표준 인프라 구성
- 배포 전 위험 요소를 운영자가 HITL로 검토
- 구축 의도를 이후 운영 판단에 재사용

---

## 5.3 모니터링 및 알람

### 기능

- 매트릭 수집/조회
- 로그 수집/검색
- 트레이스 수집/조회
- 알람 규칙 정의
- 알람 노이즈 필터링
- Service Detail 대시보드 (서비스/리소스 상세)
  - **5.1의 SLA Overview 대시보드에서 드릴다운되는 상세 화면**
  - 직접 사용자: 시스템 운영자(주연 1)

### 목적

- 고객사 서비스 상태를 통합 관제
- 운영자가 여러 도구를 직접 오가지 않도록 지원
- 단순 알람이 아니라 조치가 필요한 신호 중심으로 정리
- 매트릭/로그/트레이스가 단순 관측 데이터가 아니라 5.1에서 정의한 **SLI의 측정 원천**으로 작동한다. 즉 모든 관측이 SLA 충족 여부 판단으로 연결된다.

---

## 5.4 장애 대응(AIOps)

### 기능

- 장애 자동 탐지
- 근본 원인 분석 (RCA)
- 복구 방안 추천 (AI)
- 복구안 검토/승인 (HITL)
- 장애 자동 복구 (Self-healing)
  - 사전 승인된 정책 범위 내에서 발동

### 목적

- 알람 이후 사람이 직접 분석하던 부담 감소
- Metrics/Logs/Traces를 함께 분석해 원인 후보 제시
- 위험도에 따라 자동 조치와 HITL 승인 조치를 분리
- 운영자는 모든 알람이 아니라 중요한 판단에 집중

## 6. Phase 2 (확장) 기능

> Phase 2는 Phase 1의 기반(SLA 기준 + 구축 + 운영 + 대응)이 안정화된 이후,
> 사전 대응과 효율화로 가치를 확장하는 영역이다.

## 6.1 비용 최적화

### 기능

- 유휴 자원 탐지
- 비용 절감 권고
- SLA-비용 트레이드오프 분석

### 목적

- 운영 품질을 해치지 않는 범위에서 비용 절감
- SI 사업의 도구/인프라 운영 비용 부담 완화

## 8. AI 도구용 기준 프롬프트

```text
너는 ZeuX 프로젝트의 기획/설계/개발 보조자다.

ZeuX는 B2B 클라우드 인프라 운영 AX 솔루션이다.
SK AX 클라우드 서비스 운영팀이 여러 외부 고객사 인프라를 더 효율적으로 구축·운영하도록 돕는 Multi-Agent 기반 Cloud Infra AIOps 서비스다.

중요 방향:
- 운영자를 대체하는 서비스가 아니다.
- 운영자의 업무 효율을 높이고 역할을 실행자에서 감독자로 확장하는 서비스다.
- 모든 주요 자율 동작은 HITL(Human-in-the-Loop)을 거친다.
  AI가 안을 만들고, 운영자가 검토·승인하고, 그 후에 실행된다.
  Self-healing 같은 자율 동작도 사전 승인된 정책 범위 내에서만 발동된다.
- SLA는 ZeuX의 가치 측정 단위이자 Agent 의사결정의 기준이다.
  ZeuX는 SLA, SLI, Error Budget 세 개념을 사용한다.
  - SLA: 외부 고객사와의 계약상 약속(예: 가용성 99.9%).
  - SLI: 서비스 상태의 실시간 측정값.
  - Error Budget: SLA에서 직접 파생되는 허용 실패량.
    Agent의 자동 조치 트리거이자 SLA 위반 사전 예측의 정량 기준.
- SRE 표준의 SLO는 MVP 범위에서 의도적으로 제외했다.
  Error Budget은 SLA에서 직접 파생되도록 단순화한다.
- Phase 1 (MVP)은 IaC 인프라 구축과 모니터링/AIOps 운영을 모두 보여준다.
- 직접 사용자는 외부 고객사가 아니라 SK AX 본사 운영 담당자다.
- 외부 고객사는 결과적으로 더 빠른 구축과 안정적 운영을 제공받는다.

최신 시스템 구성:
- Phase 1 (MVP): SLA 관리, IaC 인프라 구축, 모니터링 및 알람, 장애 대응(AIOps)
- Phase 2 (확장): 비용 최적화, 용량 계획/예측

대시보드 구조:
- SLA Overview 대시보드 (SLA 관리 그룹): 고객사/앱 단위의 상위 뷰
- Service Detail 대시보드 (모니터링 및 알람 그룹): 서비스/리소스 단위의 상세 뷰
- 운영자는 Overview에서 이상 신호 발견 시 Service Detail로 드릴다운한다.

주요 기능:
1. 고객사/서비스 요구사항 입력
2. 운영 기준 해석
3. 인프라 요구사항 산출
4. Terraform 코드 생성
5. plan 검증 및 HITL 승인
6. IaC 배포 실행
7. Prometheus/Grafana/Loki/Tempo 기반 관제 구성
8. 알람 노이즈 필터링
9. RCA
10. 복구 방안 추천
11. HITL 기반 승인/자동 조치
12. 운영 리포트 생성
```

### 본질

- 클라우드 인프라 구축과 운영 사이의 반복 업무를 Agent가 흡수
- SK AX 운영팀은 같은 인력으로 더 많은 고객사 사이트 관리 가능
- Day 0 구축 산출물이 Day 2 운영 판단에 재사용됨
- OSS 관제 스택을 Agent가 조립해 상용 도구 비용 부담 완화
- HITL이 "실행자 → 감독자" 이동을 실제로 구현하는 메커니즘이자, 감사 추적 자산으로 이중 기능한다
