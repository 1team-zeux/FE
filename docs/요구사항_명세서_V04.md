# 요구사항명세서 V4.0

생성일: 2026년 5월 27일 오전 10:01

#### 통합 데이터 카탈로그

**ZeuX V04 통합 데이터 모델 카탈로그** 

step 1 마무리 산출물 (v1 → v2 갱신). 화면 1·2 입력 + SLA Bundle 출력까지의 통합 데이터 모델.

원본 입력: [상세] 1. SLA 문서 (1.1~1.4) + [상세] 2. 인프라 추가 정보 문서 (2.1~2.9). 중복·충돌은 step 1-1의 원칙 8개로 정리.

---

### 양식

| 필드명 | 설명 | 데이터 타입 (단위) | 누가 채우나 (default inline) | 필수/선택 |

규칙:

- LLM 추출 (문서 X)*는 어느 문서에서 뽑는지 inline 표기. 문서에 정보 없거나 모호하면 *챗봇 대화 보완*으로 폴백 (default 동작)
- *LLM 추천*은 ZeuX 도메인 표준 기반 제안 (계약서·문서엔 없음)
- *시스템 자동 매핑*은 default 값 또는 다른 필드에서 결정론적 변환
- *운영자 직접*은 어느 문서에도 없고 시스템도 결정 못하는 진짜 운영자 결정 영역만

### FR-iac-001 두 문서 업로드 및 검증

**요구사항 ID**: FR-iac-001

**요구사항명**: 두 문서 업로드 및 검증

**관련 액터**: 시스템 운영자 (Primary), 시스템

**기능 설명**

운영자가 화면 1의 두 업로드 영역에서 SLA 계약서 PDF와 인프라 추가 정보 문서를 각각 업로드하면, 시스템이 두 파일에 대해 형식·무결성·완전성을 검증하고 결과를 시각적으로 표시한다. 검증 통과 시 두 문서를 시스템 내부 저장소(파일 시스템 또는 객체 스토리지)에 영구 저장하고 메타데이터(파일명·크기·SHA-256 해시·업로드 시각·문서 유형)를 함께 보존한 뒤, 화면 1 하단의 "다음" 버튼을 활성화한다. 검증 실패 시 실패 유형을 운영자에게 명시하고 재업로드 경로를 제공한다. 두 문서는 한 *업로드 세션*으로 묶여 `upload_session_id`가 부여되며, 이 세션 ID가 후속 단계 FR-iac-002 LLM 파싱 트리거의 입력 키로 전달된다. 모든 업로드 이력은 감사 추적 목적으로 보존된다.

**사전 조건**

- 운영자가 SLA 계약서 PDF 파일 보유 (텍스트 PDF 형식, 스캔본은 Phase 2)
- 운영자가 인프라 추가 정보 문서 파일 보유 (PDF 또는 시스템 지원 형식)
- 운영자가 ZeuX 시스템에 인증 완료 상태로 접속
- 시스템 내부 저장소 가용 상태

**기본 흐름**

1. **화면 1 진입**
    - 운영자가 ZeuX 메인 진입점에서 "신규 고객사 온보딩" 시작 시 화면 1로 라우팅
    - 화면 1 레이아웃: 상단에 페이지 제목(*"문서 업로드"*), 중앙에 두 개의 업로드 영역이 좌우 병치, 하단에 비활성화된 "다음" 버튼, 좌측 하단에 챗봇 modal 아이콘(초기 접힘 상태로 상시 가시)
    - 두 업로드 영역에는 각각 라벨(좌: *"SLA 계약서 PDF"*, 우: *"인프라 추가 정보 문서"*) + 드래그앤드롭 zone + 파일 선택 버튼 + 업로드 상태 표시 영역이 포함
2. **운영자 문서 업로드**
    - 운영자가 SLA 계약서 PDF를 좌측 영역에 업로드 (드래그앤드롭 또는 파일 선택)
    - 운영자가 인프라 추가 정보 문서를 우측 영역에 업로드
    - 업로드 중에는 각 영역에 진행률 표시
    - 두 문서 업로드 순서는 무관
3. **시스템 검증 (각 문서별)**
    - 형식 검증: PDF MIME 타입 확인, 텍스트 PDF 여부 판별 (스캔본 차단)
    - 무결성 검증: 파일 헤더 파싱 가능 여부, 손상·암호화 여부 확인
    - 크기 검증: 시스템 제한값 이내 확인 (50MB)
    - 검증 결과를 각 업로드 영역 아래에 배지로 표시 (통과: 초록 체크, 실패: 빨강 X + 사유 텍스트)

### FR-iac-002 통합 폼 자동 채움

**요구사항 ID**: FR-iac-002

**요구사항명**: 통합 폼 자동 채움

**관련 액터**: AI Agent (LLM), 시스템, 시스템 운영자 (간접 — 결과 표시 대상)

**기능 설명**

화면 2 진입과 동시에 시스템이 LLM 파싱 작업을 자동 트리거하여, FR-iac-001에서 업로드된 두 문서를 분석하고 통합 데이터 모델 카탈로그 v2에 정의된 필드들을 자동으로 채운다. 자동 채움은 세 가지 방식으로 동시 진행된다: (1) LLM이 문서 1·2에서 *직접 추출* 가능한 필드를 뽑아 채움, (2) LLM이 ZeuX 도메인 표준 기반으로 *추천*하는 필드를 채움 (계약서·문서에 없는 정보), (3) 시스템이 *default 값이나 다른 필드 역추론 규칙*으로 자동 매핑되는 필드를 채움. 모든 자동 채움 결과는 *임시 상태*로 표시되며, 각 필드에는 신뢰도(확실/모호/추정)와 출처(문서 페이지 번호·텍스트 스니펫 또는 system_default/system_rule)가 매달려 운영자가 검토 시 추적 가능하다. SLA 항목은 MVP 범위인 4개 카테고리(Availability·Latency·RTO·RPO)로만 필터링되어 채워지며, 그 외 카테고리가 추출된 경우 제외 사실을 명시한다. 작업 완료 후 통합 폼은 FR-iac-003 운영자 검토·승인 단계 진입 가능 상태가 된다.

**사전 조건**

### FR-iac-003 운영자 폼 검토·승인

1. **폼 진입 및 임시 상태 인식**
    - FR-iac-002 완료 후 화면 2 폼이 운영자에게 노출됨
    - 폼 영역별 섹션 (1.1·1.3·2.1·2.2 등) 좌측 탭 또는 아코디언 형태로 구분
    - 각 필드는 임시 상태 배경색 옅게 강조 + 신뢰도 배지 + 출처 인라인 표시
    - 폼 상단에 진행도 표시 (예: *"47개 필수 필드 중 0개 확정"*)
2. **신뢰도 우선순위 검토 가이드**
    - 폼 상단에 *"우선 검토 필요"* 섹션 표시 — 신뢰도 *모호*·*추정* 필드를 우선 노출
    - 운영자가 해당 항목 클릭 시 폼 내 해당 위치로 스크롤 (앵커 이동)
    - 필드별 신뢰도 배지 클릭 시 출처 모달 팝업 (계약서 페이지 + 텍스트 스니펫 전문)
3. **필드별 검토 액션**
    - 액션 A — *수용*: 자동 채움 값이 맞으면 체크 버튼 클릭. 필드 상태가 *임시* → *확정*으로 전환되며 시각 강조 사라짐
    - 액션 B — *수정*: 자동 채움 값을 변경. 입력 컨트롤(텍스트·숫자·드롭다운·체크박스 등) 활성화 → 새 값 입력 → 확정 → 상태 전환
    - 액션 C — *직접 입력*: 빈 필드에 운영자가 처음 입력 (예: LLM 추출 실패 항목·자동 매핑 결정 불가 항목)
    - 각 액션 직후 시스템이 SLABundleDraft의 해당 필드를 업데이트하고 변경 이력 보존
4. **SLA 정합성 실시간 검증**
    - 운영자가 필드를 확정할 때마다 시스템이 SLA Bundle 내부 정합 규칙 자동 검증
    - 위반 감지 시 (예: SLA RTO 30분 vs `secondary_region`=null) 해당 필드 옆에 경고 배지 표시 + FR-iac-004 챗봇 트리거 활성화
    - 챗봇 알림 배지가 좌측 하단 아이콘에 표시되어 운영자에게 명확화 필요 신호
5. **진행도 업데이트**
    - 필드 확정 시마다 폼 상단 진행도 갱신 (예: *"47개 필수 필드 중 23개 확정"*)
    - 모든 필수 필드 확정 시 진행도 100% + *"확인"* 버튼 활성화
6. **운영자 일시 저장 (Implicit)**
    - 검토 중 운영자가 화면을 벗어나도 SLABundleDraft 상태는 보존 — 재진입 시 이어서 작업 가능
    - 자동 저장 주기 — 필드 확정 액션마다 즉시 (별도 *"저장"* 버튼 없이 implicit)

**예외 흐름**

- ① **필수 필드 미확정 상태에서 우회 진행 시도** — *"확인"* 버튼은 비활성 상태라 클릭 불가. 우회 시도 시 *"미확정 필수 필드가 있습니다"* 토스트 메시지 + 미확정 필드 시각 강조 (빨강 테두리)
- ② **운영자 수정값이 enum·타입 규칙 위반** — 예를 들어 `service_tier`에 잘못된 값 입력 시 입력 컨트롤에서 즉시 검증 실패 표시 (빨강 테두리 + 메시지) + 확정 차단
- ③ **운영자 수정값이 SLA 정합 위반** — FR-iac-004 챗봇 트리거 활성화. 운영자는 (1) 챗봇 답변으로 자동 보완, (2) 직접 다른 필드 수정으로 해결, (3) 일단 진행 후 추가 검토 중 선택 가능
- ④ **자동 채움 값과 운영자 수정값 충돌 이력 기록** — 운영자가 LLM 추천을 거부·수정한 경우 변경 전후 값이 감사 로그에 보존 (LLM 추천 품질 개선용 데이터 누적)
- ⑤ **시스템 상태 손실** — 세션 만료·브라우저 종료 등으로 임시 저장 상태 손실 가능성. 자동 저장이 즉시 동작하지만 만일 동기화 지연 중 손실 시 마지막 자동 저장 시점부터 복구

**사후 조건**

- SLABundleDraft의 모든 필수 필드가 *확정* 상태로 전환됨
- 각 필드 확정 이력(액션 유형·이전 값·새 값·확정 시각)이 감사 로그에 보존
- 운영자 수정 이력이 LLM 추천 품질 개선용 데이터로 누적
- *"확인"* 버튼이 활성화되어 FR-iac-005 진입 가능
- SLA 정합 위반 미해결 항목이 있다면 FR-iac-004 챗봇 modal에서 미해결 상태로 추적됨

### FR-iac-004 챗봇 modal 능동 명확화 질문

**요구사항 ID**: FR-iac-004

**요구사항명**: 챗봇 modal 능동 명확화 질문

**관련 액터**: AI Agent (LLM), 시스템 운영자

**기능 설명**

화면 2에서 통합 폼의 빈 필드·신뢰도 모호 필드·SLA 정합 위반이 감지되면 LLM이 좌측 하단 챗봇 modal에서 자연어 명확화 질문을 능동적으로 발동한다. 질문은 사전 정의된 3단계 우선순위 (P0 필수 / P1 중요 / P2 선택)로 점진 제시되며, 운영자가 자연어로 답변하면 LLM이 해석해 해당 폼 필드에 자동 반영하고 *확정* 상태로 전환한다. 질문은 두 가지 유형으로 분류: (A) *미입력 질문* — 빈 필드·신뢰도 모호 필드 대상, (B) *SLA 정합 질문* — SLA Bundle 내부 정합 위반 발견 시. SLA 정합 질문에는 어느 SLA 항목과 어떻게 충돌하는지가 함께 제시되고, 운영자에게 두 가지 해결 경로가 제공된다 — (1) 폼 필드 수정, (2) SLA 자체 재검토. 챗봇 modal은 화면 2 전 영역에서 좌측 하단 아이콘으로 상시 접근 가능하며, 발동 시 알림 배지로 운영자에게 인지 신호를 보낸다. 모든 챗봇 대화는 감사 로그로 보존된다.

**사전 조건**

- FR-iac-002 완료 — 통합 폼이 임시 상태로 채워짐
- 챗봇 modal이 좌측 하단에 활성 상태로 존재 (화면 2 진입 시점부터)
- LLM API 가용 상태

**기본 흐름**

1. **명확화 필요 필드 식별**
    - 시스템이 SLABundleDraft를 스캔하여 명확화 대상 필드 식별
        - 빈 필수 필드 (LLM 추출 실패 + 자동 매핑 결정 불가)
        - 신뢰도 *모호*·*추정* 필드
        - SLA 정합 위반 감지 필드 (FR-iac-003 단계 4에서 트리거)
    - 각 필드에 사전 정의된 우선순위 (P0/P1/P2) 부여
    - 신뢰도 *추정* 필드는 원래 우선순위에서 한 단계 상향 (운영자 확인 강제)
2. **알림 배지 표시**
    - 챗봇 modal 좌측 하단 아이콘에 알림 배지 표시 (예: 빨간 점 + 미해결 항목 개수)
    - 운영자가 다른 인터랙션 중에도 명확화 필요 인지 가능
3. **챗봇 modal 발동**
    - 운영자가 아이콘 클릭 시 modal 펼침 (또는 첫 P0 발동 시 자동 펼침)
    - modal은 좌측 sliding panel 형태로 표시되어 폼 영역과 병존 — 챗봇 보면서 폼 수정 가능
4. **P0 우선 질문 생성 및 표시**
    - LLM이 첫 P0 대상 필드에 대해 자연어 질문 생성
        - 유형 A 예시: *"고객사명이 계약서에서 모호하게 추출되었습니다. 'SK텔레콤'이 맞나요? 아니면 다른 명칭으로 등록할까요?"*
        - 유형 B 예시: *"SLA에 RTO 30분 항목이 정의돼 있는데, secondary_region이 설정되지 않았습니다. RTO 30분 달성하려면 보조 지역에 백업 환경이 필요합니다. (1) 보조 region을 설정하시겠어요? (2) SLA의 RTO를 재검토하시겠어요?"*
    - 질문 본문에 *어느 폼 필드와 연결되는지*가 inline 표시되며, 우측 폼의 해당 필드가 시각 강조됨
5. **운영자 자연어 답변**
    - 운영자가 modal 입력창에 자연어 답변 (예: *"SK텔레콤 맞아요"*, *"ap-northeast-3로 secondary 설정해주세요"*)
    - 클릭 옵션이 아니라 자연어 입력 (chat-style 인터페이스)
6. **LLM 답변 해석 및 폼 반영**
    - LLM이 운영자 자연어 답변을 해석하여 해당 폼 필드 값으로 변환
    - 시스템이 SLABundleDraft의 해당 필드 업데이트 + 신뢰도 *"확실"* + 출처 *"chat_clarify"*로 메타 변경
    - 우측 폼의 해당 필드가 즉시 갱신되어 *확정* 상태 시각 표시
    - 변경 이력 (질문·답변·반영된 필드값·변경 전후)이 감사 로그에 보존
7. **다음 우선순위 진행**
    - 같은 P0 안에서 남은 필드가 있으면 다음 질문 자동 생성
    - P0 모두 해결되면 P1 시작, P1 모두 해결되면 P2 시작
    - 같은 우선순위 안에서 어떤 필드를 먼저 물을지는 LLM이 컨텍스트 보고 결정
8. **SLA 정합 질문(유형 B) 후속 처리**
    - 운영자가 *(1) 폼 필드 수정* 선택 → 답변 해석 후 해당 필드 업데이트 (단계 6과 동일)
    - 운영자가 *(2) SLA 재검토* 선택 → *"SLA 재검토는 화면 1로 복귀해 SLA 계약서를 다시 검토해야 합니다. 이번 MVP 범위 밖이라 일단 폼 수정으로 진행할까요?"* 식의 안내 (본격 SLA 재검토는 Phase 2 또는 별도 흐름)
9. **명확화 완료 및 챗봇 modal 상태 전환**
    - 모든 명확화 대상 필드가 *확정* 상태로 전환되면 알림 배지 사라짐
    - modal은 운영자가 닫을 때까지 열려있되 *"명확화 완료 — 추가 질문이 있으시면 물어보세요"* 상태 메시지 표시

**예외 흐름**

- ① **운영자 답변이 LLM 해석 불가** — *"답변을 명확히 이해하지 못했습니다. 다시 한 번 말씀해주시거나, 폼에서 직접 입력해주세요."* 메시지 + 재질문 1회 시도 후 실패 시 폼 직접 입력 경로 안내
- ② **운영자가 챗봇 무시** — modal을 닫고 폼에서 직접 작업 가능. 다만 P0 필수 필드가 미해결 상태면 *"확인"* 버튼이 활성화되지 않아 진행 차단됨
- ③ **LLM 호출 실패·타임아웃** — 챗봇 modal에 *"챗봇 응답 실패 — 폼에서 직접 입력해주세요."* 메시지 + 운영자 직접 입력 경로 활성화
- ④ **운영자가 *"이 항목은 모르겠어요"* 또는 *"건너뛰기"*** — P2 항목이면 *"보류"* 상태로 표시하고 진행 허용. P0·P1 필수면 *"필수 항목이라 보류 불가"* 안내
- ⑤ **운영자가 챗봇 답변과 폼 직접 입력을 동시 시도** — 마지막 액션 우선 (last-write-wins). 충돌 시 시스템이 *"최근 답변으로 갱신됨"* 알림

**사후 조건**

- 명확화 대상 필드들이 *확정* 상태로 전환됨 (또는 P2 *보류* 상태)
- 챗봇 대화 이력 (질문·답변·반영된 필드값·우선순위·변경 전후)이 감사 로그에 보존
- SLABundleDraft가 갱신되어 폼 진행도 증가
- SLA 정합 위반 미해결 항목이 있다면 그 상태가 추적 가능하게 표시됨

### FR-iac-005 SLA Bundle 묶기 및 화면 전환

**요구사항 ID**: FR-iac-005

**요구사항명**: SLA Bundle 묶기 및 화면 전환

**관련 액터**: 시스템 운영자 (Primary), 시스템

**기능 설명**

운영자가 화면 2에서 모든 필수 필드를 확정한 후 "확인" 버튼을 클릭하면, 시스템이 SLABundleDraft 임시 저장 단위의 모든 확정 필드와 시스템 자동 매핑 결과, Bundle 자체 메타(`bundle_id`·`bundle_version`·`active_period_start`·`active_period_end`·`created_at`·`updated_at`)를 단일 SLA Bundle로 묶어 DB에 영구 저장하고 화면 3으로 전환한다. SLA Bundle은 카탈로그 v2 구조 그대로 47개 확정 필드 + 자동 매핑 11개 + Bundle 메타 6개를 포함한 단일 단위로, *후속 화면 3 토폴로지 결정과 화면 4 Terraform 코드 생성의 단일 진실 공급원*으로 참조된다. 저장 성공 후 SLABundleDraft 임시 저장 단위는 archive 또는 삭제 처리되어 *active 상태의 SLA Bundle*이 해당 고객사·서비스에 대해 유일하게 존재한다. 저장 직후 화면 3 진입 트리거가 활성화되며 `bundle_id`가 입력 파라미터로 전달된다.

**사전 조건**

- FR-iac-003 완료 — SLABundleDraft의 모든 필수 필드가 *확정* 상태
- "확인" 버튼이 활성화된 상태 (FR-iac-003 단계 5에서 진행도 100% 달성)
- DB 가용 상태 (PostgreSQL + JSONB 권장 구조)
- 시스템 트랜잭션 처리 가능 상태

**기본 흐름**

1. **확인 버튼 클릭 감지**
    - 운영자가 화면 2 하단 "확인" 버튼 클릭
    - 클릭 직후 버튼 비활성화 (중복 클릭 방지) + 처리 중 로딩 인디케이터 표시
    - 운영자에게 *"SLA Bundle 저장 중..."* 진행 상태 메시지
2. **최종 검증 (안전장치)**
    - 시스템이 SLABundleDraft의 모든 필수 필드가 *확정 상태*인지 재검증
    - 필드 간 정합성 최종 점검 (SLA-인프라 정합 위반 잔존 여부 확인)
    - 검증 통과 시 다음 단계 진행, 실패 시 예외 흐름 ②·③ 처리
3. **Bundle 자체 메타 자동 부여**
    - `bundle_id`: UUID 생성
    - `bundle_version`: 첫 저장이면 `v1`, 갱신이면 `v2`·`v3`...

**요구사항 ID**: FR-iac-008

### FR-iac-009 Terraform plan 해석·표시

**요구사항 ID**: FR-iac-009

**요구사항명**: Terraform plan 해석·표시

**관련 액터**: AI Agent (LLM), 시스템, 시스템 운영자 (간접 — 결과 표시 대상)

**기능 설명**

FR-iac-008에서 `ready_for_plan` 상태인 작업 디렉토리에 대해 `terraform plan`을 실행하고 raw 출력을 4차원(변경 유형·위험도·SLA 영향·비용 영향)으로 재분류해 운영자에게 의사결정 가능한 형태로 표시한다. 변경 유형은 추가·수정·교체·삭제로 자동 분류되며, 위험도는 *교체·삭제·기존 리소스 영향*을 '높음', *in-place 수정 일부 속성*을 '중간', *신규 추가*를 '낮음'으로 산출한다. SLA 영향도는 활성 SLA Bundle의 SLI Mapping 규칙과 변경 리소스를 대조해 산출하며, 비용 영향은 Infracost 기반 월 비용 변화량으로 산출. 위험도 '높음' 또는 SLA 부정 영향이 감지되면 `plan_review_required` 상태로 진입하고 운영자에게 *승인 후 진행·코드 수정·토폴로지 재검토* 3가지 선택지를 제시한다.

**사전 조건**

- FR-iac-008 완료 — 작업 디렉토리 `ready_for_plan` 상태
- 활성 SLA Bundle의 SLI Mapping 규칙이 시스템에 정의됨
- Infracost 도구 또는 단가 추정 모듈 가용

**기본 흐름**

1. **자동 트리거 및 plan 실행**
    - FR-iac-008의 `ready_for_plan` 상태 전환 직후 본 단계 자동 발동
    - 작업 디렉토리에서 `terraform init` (provider·module download) → `terraform plan -out=plan.tfplan` 순차 실행
    - 실행 중 로그를 실시간 캡처
2. **raw plan 출력 파싱**
    - `terraform show -json plan.tfplan` 으로 plan을 구조화 JSON으로 변환
    - 각 리소스 변경을 `resource_changes[]` 배열로 추출, 액션 타입(`create`·`update`·`delete`·`replace`) 분류
3. **변경 유형 분류 (차원 1)**
    - 추가 (`create`) / 수정 (`update`) / 교체 (`replace`) / 삭제 (`delete`)
    - 각 카테고리별 리소스 목록 정렬
4. **위험도 산출 (차원 2)**
    - **높음**: `delete` 또는 `replace` 액션, 또는 기존 prod 리소스에 영향 주는 `update`
    - **중간**: `update`의 일부 속성 변경 (예: instance_type 변경, tag 변경)
    - **낮음**: 신규 `create` 액션 (기존 영향 없음)
    - 각 리소스에 위험도 라벨 부착
5. **SLA 영향도 산출 (차원 3)**
    - 활성 SLA Bundle의 각 SLA 항목별 SLI Mapping 규칙 로드 (예: Customer Portal Web의 availability → ALB target group health)
    - 변경 리소스가 SLI 측정 대상 리소스와 일치하면 *영향 있음* 표시
    - 영향 유형 분류 — *긍정*(개선 기대, 예: Read Replica 추가) / *중립*(영향 없음) / *부정*(저하 예상, 예: instance 사이즈 축소)
6. **비용 영향 산출 (차원 4)**
    - Infracost 또는 단가 추정 모듈로 *기존 비용* vs *plan 적용 후 비용* 차이 산출
    - 카테고리별 (컴퓨팅·DB·네트워크 등) 변화량 명시
    - Infracost 호출 실패 시 추정값 fallback (단, 추정 표시)
7. **분류 결과 패키징 (`plan_summary`)**
    - 4차원 분류 결과를 단일 JSON 객체로 정리
    - 각 리소스마다 [resource_address·action·위험도·SLA 영향·비용 변화] 한 행
    - 카테고리별 집계 (예: "추가 12건·수정 3건·교체 1건·삭제 0건, 위험도 높음 1건")
8. **상태 분기**
    - 위험도 '높음' 0건 AND SLA 부정 영향 0건 → `plan_passed` 전환, FR-iac-010 진입 트리거
    - 위험도 '높음' ≥ 1건 OR SLA 부정 영향 ≥ 1건 → `plan_review_required` 전환, 운영자 선택 대기
    - terraform plan 자체 실패 → `plan_failed` 전환, 예외 ① 흐름
9. **운영자 표시 (plan_review_required 시)**
    - 화면 4에 `plan_summary` 시각화: 4차원 분류 표 + 위험도 높음 항목 시각 강조

**요구사항 ID**: FR-iac-010

**요구사항명**: Terraform apply 실행

**관련 액터**: 시스템 운영자 (Primary), 시스템

**사전 조건**

**기본 흐름**

    - 클릭 직후 *'배포 시작'* 버튼 비활성화 (중복 클릭 방지)
3. **`terraform apply -auto-approve` 실행**
    - 작업 디렉토리에서 `terraform apply -auto-approve plan.tfplan` 실행
    - stdout·stderr를 실시간 캡처해 백엔드 → WebSocket → 화면 4로 스트리밍
    - 작업 디렉토리 상태 `applying` 전환

- ④ **`terraform destroy` 도중 실패 (전체 롤백 선택 시)** — 의존성·외부 연결 등으로 destroy 도중 일부 리소스가 삭제 안 됨 시 *"롤백 일부 실패 — 수동 정리 필요"* 알림 + 미삭제 리소스 목록 + AWS 콘솔 링크 제공
- ⑤ **state file 저장 실패** — apply는 성공했으나 S3 backend 저장이 실패 시 *"state 저장 실패 — 로컬 state 파일 보존됨"* 경고 + 시스템 관리자 개입 요청. 로컬 state 파일은 작업 디렉토리에 보존되어 수동 복구 가능
- ⑥ **WebSocket 연결 끊김** — 화면 4와 백엔드의 실시간 스트리밍 채널이 끊기는 경우 운영자가 *진행 상태를 못 봄*. 백엔드는 apply 계속 진행. 재연결 시 last_event_id 기반으로 누락 이벤트 재전송

**사후 조건**

- 작업 디렉토리 상태가 `applied`·`partially_applied`·`apply_failed` 중 하나로 전환

    - 전체 통과 → 서비스 status `구축중` → `운영중` 자동 전환
    - 일부 실패 → 서비스 status `verification_failed` 전환
    - 검증 결과·실패 항목 상세·재현 방법이 감사 로그 보존
11. **운영자 표시 및 후속 처리**
    - 전체 통과 시: *"안정성 검증 완료 — 서비스 운영중 상태로 전환됨"* 토스트 + FR-mon-004 모니터링 설정 진입 버튼 표시 + 화면 4 종료 가능
    - 일부 실패 시: 화면 4에 *실패 카테고리 상세* 표시 + 3가지 선택지 버튼:
        - *"재실행"* — 검증 8개 카테고리 다시 수행 (일시적 문제일 수도)
        - *"FR-iac-008 코드 수정"* — 코드 생성 단계로 복귀, 변수 매핑·모듈 조정
        - *"FR-iac-006 토폴로지 재검토"* — 토폴로지 결정 단계로 복귀

**예외 흐름**

- ① **검증 도구 호출 실패** — AWS API rate limit·네트워크 오류 등으로 일부 카테고리 검증이 호출 자체 실패 시 *"카테고리 X 검증 실행 실패 — 잠시 후 재시도"* + 자동 backoff 재시도 3회. 그래도 실패 시 *"검증 일시 중단 — 운영자 재실행 요청 필요"*
- ② **모니터링 송출이 아직 데이터 도달 안 함** — 카테고리 6 검증 시 본사 백엔드에 데이터 미수신 시 *송출 컴포넌트 자체 헬스* 와 *데이터 수신* 을 분리 평가. 컴포넌트는 정상이지만 데이터 도달 지연 (5분 대기 후 재확인). 5분 후에도 미수신이면 송출 경로 실패로 판정
- ③ **운영자가 일부 실패 무시하고 *"운영중 강제 전환"* 요청** — *"위험 — 검증 X·Y 카테고리 실패 상태로 운영 진입 시 향후 장애 발생 가능"* 경고 후 명시적 확인 시에만 status 강제 전환 (감사 로그에 *"운영자 강제 전환"* 명시)
- ④ **검증 중 운영자가 화면 이탈** — 검증 백엔드는 계속 진행. 재진입 시 진행 상태·완료된 카테고리 결과 복원
- ⑤ **토폴로지 정합 위반 (카테고리 7) — 결정 의도와 실제 배포가 다름** — 이건 *심각한 오류*. terraform apply 자체는 성공했으나 결과가 토폴로지 의도와 어긋남. 운영자에게 *"심각 — 토폴로지 결정과 실제 배포 불일치. FR-iac-008 코드 수정 권장"* 알림 + 추적 가능한 상세 (어느 차원의 어느 결정이 어떻게 어긋났는지)
- ⑥ **카테고리 1 drift 감지** — state file과 실제 AWS가 다른 경우 (예: 누군가 콘솔에서 수동 변경) → *"drift 감지 — terraform refresh 후 재검증 권장"* + 운영자 결정 대기

**사후 조건**

- 8개 카테고리 검증 결과 (`verification_report` JSON) 보존
- 서비스 status가 `운영중`·`verification_failed` 중 하나로 전환됨
- `운영중` 전환 시: FR-mon-004 진입 트리거 활성화, 운영자에게 모니터링 설정 버튼 노출
- `verification_failed` 전환 시: 운영자가 재실행·코드 수정·토폴로지 재검토 중 선택 가능
- 검증 이력 (각 카테고리 결과·실행 시간·실패 상세·운영자 선택) 감사 로그 보존
- 운영자 *"강제 전환"* 선택 시 그 사실이 감사 로그에 명시되어 향후 책임 추적 가능
