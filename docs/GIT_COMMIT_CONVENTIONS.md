# 📝 Git 커밋 컨벤션 규칙 지침서

## 1. 커밋 메시지 기본 구조

커밋 메시지는 기본적으로 제목(Subject), 본문(Body), 바닥글(Footer)의 3단 구조로 작성하며, 각 섹션은 빈 줄(Blank Line)로 구분합니다.

Plaintext

```
Type: Subject (제목)

Body (본문 - 생략 가능)

Footer (바닥글 - 생략 가능)
```

## 2. 제목 규칙 (Subject)

제목은 커밋의 핵심 내용을 한눈에 파악할 수 있도록 50자 이내로 간결하게 작성합니다.

### 📌 커밋 타입(Type) 종류

가장 중요한 부분으로, 접두어(Prefix)를 통해 어떤 종류의 변경사항인지 명시합니다.

| **타입(Type)** | **설명** | **예시** |
| --- | --- | --- |
| **`feat`** | 새로운 기능 추가 | `feat: 사용자 로그인 기능 구현` |
| **`fix`** | 버그 수정 | `fix: 이메일 중복 검사 로오류 수정` |
| **`docs`** | 문서 수정 (README, 위키, 주석 등) | `docs: README.md 아키텍처 다이어그램 추가` |
| **`style`** | 코드 의미에 영향을 주지 않는 변경 (포맷팅, 세미콜론 누락 등) | `style: 인덴트 탭을 4스페이스로 통일` |
| **`refactor`** | 코드 리팩토링 (기능 추가나 버그 수정이 없는 구조 개선) | `refactor: 중복 코드 메서드 분리` |
| **`test`** | 테스트 코드 추가 및 수정 | `test: 인증 서비스 단위 테스트 추가` |
| **`chore`** | 빌드 업무, 패키지 매니저 설정, 인프라 변경 (소스 코드 외적인 부분) | `chore: 깃이그노어(.gitignore) 환경변수 추가` |
| **`perf`** | 성능 개선을 위한 코드 변경 | `perf: 데이터베이스 인덱스 추가를 통한 쿼리 최적화` |
| **`ci`** | CI 설정 파일 및 스크립트 수정 | `ci: GitHub Actions 배포 워크플로우 수정` |

### ⚠️ 제목 작성 시 주의사항

- 타입(Type) 뒤에는 콜론과 한 칸의 공백(`:` )을 둡니다.
- 제목 끝에 **마침표(`.`)를 찍지 않습니다.**
- 영문으로 작성할 경우 첫 글자는 대문자가 아닌 **소문자**로 시작하며, 명령조(Imperative tone)로 작성합니다. (예: `Fix...` 보다는 `fix...`, `Fixed...` 보다는 `fix...`)

## 3. 본문 규칙 (Body)

본문은 꼭 필요한 경우가 아니라면 생략이 가능합니다. (보통 `feat`, `fix`, `refactor`처럼 설명이 더 필요한 경우에 사용합니다.)

- **무엇을(What)** 변경했는지와 **왜(Why)** 변경했는지를 상세히 작성합니다. (어떻게(How) 변경했는지는 코드에 드러나므로 굳이 적지 않습니다.)
- 한 줄당 72자를 넘지 않도록 줄바꿈을 해주는 것이 좋습니다.

Plaintext

```
feat: 다크모드 테마 적용 기능 추가

- 사용자의 시스템 설정에 따라 다크모드가 자동으로 활성화되도록 구현함
- 야간 시인성 확보 및 배터리 절약을 요구하는 유저 피드백 반영
```

## 4. 바닥글 규칙 (Footer)

바닥글 역시 생략이 가능하며, 주로 **이슈 트래킹**이나 Breaking Changes(하위 호환성을 깨뜨리는 변경사항)를 명시할 때 사용합니다.

- **이슈 연동:** 해결한 이슈 번호를 적어 자동으로 닫히도록 설정합니다. (Keywords: `Closes`, `Fixes`, `Resolves`)
- **Breaking Change:** 큰 변화가 있을 때 `BREAKING CHANGE:` 단어로 시작하여 명시합니다.

Plaintext

```
fix: 결제 페이지 API 타임아웃 예외 처리

- 네트워크 불안정 시 결제 요청이 무한 대기하는 현상 수정
- 5초 타임아웃 후 사용자에게 알림창 팝업 구현

Closes #142
```

## 5. 실전 팁 및 체크리스트

> 💡 **좋은 커밋을 위한 Golden Rules**
> 
> 1. **커밋은 하나의 작업 단위로 쪼개세요.** 한 커밋에 기능 추가, 버그 수정, 리팩토링이 섞여 있으면 컨벤션을 지키기 어렵고 히스토리 추적이 힘들어집니다.
> 2. **도구 활용하기:** 팀 단위로 컨벤션을 강제하고 싶다면 `commitlint`나 `Husky` 같은 도구를 활용해 커밋 메시지가 규칙에 맞지 않으면 커밋이 되지 않도록 자동화할 수 있습니다.
