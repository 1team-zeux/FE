### FR-iac-002 통합 Form 자동 채움 및 조건부 활성화

**요구사항 ID**: FR-iac-002

**요구사항명**: 통합 Form 자동 채움 및 조건부 활성화

**관련 액터**: AI Agent(LLM), 시스템, 시스템 운영자(간접 — 결과 표시 대상)

**기능 설명**

화면 2 진입과 동시에 시스템이 `upload_session_id`를 입력으로 Service Bundle Builder Agent를 자동 실행하여, FR-iac-001에서 업로드된 SLA 계약서와 인프라 추가 정보 문서를 통합 분석하고 사전 정의된 Service Bundle Form Schema의 필드들을 자동으로 채운다.

Service Bundle Form Schema는 시스템에 고정 정의되어 있으며, LLM이 Form 구조나 필드 구조를 새로 생성하지 않는다. LLM은 고정 Schema 안에서 문서 기반 값 추출, ZeuX 도메인 표준 기반 값 추천, 단위 정규화, 문서 간 의미 매핑, 모호값 후보 생성을 수행한다. 시스템은 서비스 유형(web/api/batch), SLA category(Availability·Latency·RTO·RPO), workload_type, measurement_filter 유무, DB/스토리지 필요 여부, 외부 노출 여부, 상태 저장 여부에 따라 서비스별 Form 섹션과 필드를 동적으로 활성화 또는 비활성화한다.

자동 채움은 세 가지 방식으로 동시 진행된다.

1. LLM이 문서 1·2에서 직접 추출 가능한 필드를 채움
2. LLM이 ZeuX 도메인 표준 기반으로 추천 가능한 필드를 채움
3. 시스템이 default 값 또는 역추론 규칙으로 자동 매핑 가능한 필드를 채움

모든 자동 채움 결과는 임시 상태로 표시되며, 각 필드에는 신뢰도(확실/모호/추정), 출처(doc1_contract/doc2_infra/system_default/system_rule/llm_recommendation), 문서 페이지 번호·텍스트 스니펫 또는 rule_id가 함께 매달린다.

SLA 항목은 MVP 범위인 4개 카테고리(Availability·Latency·RTO·RPO)만 활성 SLA 항목으로 포함한다. Correctness 등 MVP 범위 외 카테고리가 추출된 경우 삭제하지 않고 Phase 2 후보 항목으로 분리 표시한다. SLA 항목 중 `measurement_filter`가 존재하는 경우 L3 endpoint-level SLA로, 존재하지 않는 경우 L2 service-level SLA로 결정론적으로 분류한다.

작업 완료 후 통합 Form은 FR-iac-003 운영자 검토·승인 단계 진입 가능 상태가 된다.

    - 시스템은 두 문서에서 추출한 서비스 목록을 기준으로 `services[]` 객체를 생성한다.
    - 각 서비스 객체는 다음 정보를 포함한다.
        - `service_id`
        - `service_name`
        - `service_type`
        - `workload_type`
        - `service_tier`
        - `user_target`
        - `description`
    - 서비스 유형은 기본적으로 문서 값을 우선 사용하되, 누락된 경우 LLM이 서비스 설명과 SLA 항목을 기반으로 추정한다.
    - 서비스 유형 판정이 불확실한 경우 해당 서비스는 공통 필드만 활성화하고, 서비스 유형 판정을 FR-iac-004 P0 질문 대상으로 등록한다.
7. **SLA Items 배열 생성**
    - 시스템은 각 서비스에 연결된 SLA 항목을 `sla_items[]` 배열로 생성한다.
    - 각 SLA 항목은 다음 정보를 포함한다.
        - `sla_item_id`
        - `service_id`
        - `category`
        - `sla_level`
        - `target_value`
        - `measurement_window`
        - `measurement_formula`
        - `measurement_point`
        - `measurement_filter`
        - `exclusion_conditions`
        - `phase_scope`
    - MVP 범위의 SLA 항목은 `phase_scope=mvp`로 표시한다.
    - Correctness 등 MVP 범위 외 항목은 `phase_scope=phase2_candidate`로 표시하고 기본 비활성화한다.
8. **LLM 추천 — 도메인 표준 기반 필드 채움**
    - 계약서·문서에 없거나 명시가 부족한 필드를 ZeuX 도메인 표준 기반으로 LLM이 추천한다.
    - 추천 대상 예시:
        - `service_tier`
        - `workload_type`
        - `measurement_formula`
        - `measurement_point`
        - `sli_mapping_candidate`
        - `monitoring_signal_candidate`
    - 추천 필드는 `source=llm_recommendation`으로 표시한다.
    - 추천 근거에는 참조한 문서 값, 서비스 유형, SLA category, ZeuX 표준 규칙을 함께 표시한다.
    - 추천값은 운영자 승인 전까지 임시 상태로 유지된다.
9. **시스템 자동 매핑 — Default 및 역추론 필드 채움**
    - 시스템은 default 값과 rule 기반 역추론 값을 자동 매핑한다.
    - default 적용 예시:
        - `environment=prod`
        - `csp=aws`
        - `encryption_required=true`
        - `audit_log_required=true`
        - `least_privilege=true`
        - `cost_alert_threshold=[80,100]`
        - `db_external_access=false`
        - `internal_service_external_exposure=false`
    - 역추론 적용 예시:
        - `multi_az_required` ← `service_tier` 기반
        - `failover_required` ← RTO 기반
        - `backup_required` ← RPO 기반
        - `replication_required` ← RPO 및 정합성 중요도 기반
    - 자동 매핑 필드는 `source=system_default` 또는 `source=system_rule`로 표시한다.
10. **조건부 필드 활성화/비활성화**
    - 시스템은 서비스 유형, SLA category, workload_type, 데이터 요구사항을 기준으로 Form 필드를 활성화 또는 비활성화한다.
    - `service_type=web`인 경우 다음 필드를 우선 활성화한다.
        - RPS
        - peak RPS
        - 최대 동시 사용자
        - Availability SLA
        - Latency SLA
        - 외부 사용자 진입점
        - 정적 리소스/오브젝트 저장
        - CDN 또는 CloudFront 후보
    - `service_type=api`인 경우 다음 필드를 우선 활성화한다.
        - TPS
        - peak TPS
        - peak write rate
        - 외부 API dependency
        - endpoint-specific SLA
        - RPO
        - DB 정합성
        - Trace 수집 필요 여부
    - `service_type=batch`인 경우 다음 필드를 우선 활성화한다.
        - batch schedule
        - max concurrent jobs
        - checkpoint storage
        - RTO
        - RPO
        - Correctness 참고 지표
        - 재처리 정책
    - DB 저장 필요 여부가 false인 경우 DB 상세 필드는 비활성화하고 `not_applicable`로 표시한다.

    - 외부 직접 노출 불허 조건이 있는 경우 public endpoint 관련 필드는 비활성화하거나 internal-only 값으로 고정한다.
    - 비활성 필드는 화면에서 접힘 또는 비활성 상태로 표시되며, 후속 토폴로지 추천·Terraform 코드 생성·모니터링 정책 생성에서 기본 참조 대상에서 제외된다.
11. **카테고리 필터링 및 Phase 분리**

### FR-iac-005 SLA Bundle 묶기 및 화면 전환

**요구사항 ID**: FR-iac-005

**요구사항명**: SLA Bundle 묶기 및 화면 전환

**관련 액터**: 시스템 운영자(Primary), 시스템

**기능 설명**

운영자가 화면 2에서 모든 활성 필수 필드를 확정한 후 "확인" 버튼을 클릭하면, 시스템이 `SLABundleDraft` 임시 저장 단위의 확정 필드, 시스템 자동 매핑 결과, 서비스별 활성/비활성 필드 상태, LLM 추천값 승인 이력, Bundle 자체 메타(`bundle_id`·`bundle_version`·`active_period_start`·`active_period_end`·`created_at`·`updated_at`)를 단일 SLA Bundle로 묶어 DB에 영구 저장하고 화면 3으로 전환한다.

SLA Bundle은 고정 Service Bundle Schema를 따르되, 서비스별 활성 필드와 비활성 필드 상태를 함께 포함한다. 서비스 유형에 따라 활성 필드 수는 달라질 수 있으므로, 비활성 필드는 `not_applicable` 상태로 저장되어 후속 토폴로지 추천, Terraform 코드 생성, SLA 기반 모니터링 정책 생성에서 기본 참조 대상에서 제외된다.

저장된 SLA Bundle은 화면 3 토폴로지 결정, 화면 4 Terraform 코드 생성, 이후 SLA 기반 모니터링 정책 생성의 단일 진실 공급원으로 참조된다. 저장 성공 후 `SLABundleDraft`는 archive 또는 삭제 처리되어 active 상태의 SLA Bundle이 해당 고객사·서비스에 대해 유일하게 존재한다. 저장 직후 화면 3 진입 트리거가 활성화되며 `bundle_id`가 입력 파라미터로 전달된다.

---

**사전 조건**

- FR-iac-003 완료 — `SLABundleDraft`의 모든 활성 필수 필드가 확정 상태
- P0 명확화 질문이 모두 해결된 상태
- "확인" 버튼이 활성화된 상태
- DB 가용 상태
- 시스템 트랜잭션 처리 가능 상태
- Service Bundle Schema v2가 시스템에 적용된 상태

**기본 흐름**

1. **확인 버튼 클릭 감지**
    - 운영자가 화면 2 하단 "확인" 버튼 클릭
    - 클릭 직후 버튼 비활성화
    - 중복 클릭 방지를 위해 처리 중 로딩 인디케이터 표시
    - 운영자에게 "SLA Bundle 저장 중..." 진행 상태 메시지 표시
2. **최종 검증**
    - 시스템이 `SLABundleDraft`의 모든 활성 필수 필드가 확정 상태인지 재검증한다.
    - 비활성 필드는 확인 버튼 활성화 조건과 최종 검증 대상에서 제외하되, `not_applicable` 상태가 올바르게 부여되어 있는지 확인한다.
    - P0 명확화 질문이 남아 있는지 확인한다.
    - SLA-인프라 정합성 위반이 잔존하는지 확인한다.
    - `not_applicable` 처리된 필드가 후속 토폴로지·Terraform·모니터링 단계의 필수 입력을 잘못 제외한 것은 아닌지 검증한다.
    - 검증 통과 시 다음 단계로 진행한다.
3. **서비스별 최소 구조 검증**
    - 각 서비스 객체가 최소 필수 정보를 가지는지 확인한다.
    - 검증 항목:
        - 각 service는 `service_id`, `service_name`, `service_type`, `workload_type`을 가져야 한다.
        - 각 service는 최소 1개 이상의 SLA item 또는 운영 기준을 가져야 한다.
        - web/api 서비스는 Availability 또는 Latency 중 최소 1개 이상의 활성 SLA 항목을 가져야 한다.
        - RPO가 있는 서비스는 backup 또는 replication 관련 필드를 가져야 한다.
        - RTO가 있는 서비스는 failover 또는 recovery strategy 관련 필드를 가져야 한다.
        - L3 endpoint SLA가 있는 경우 `measurement_filter`와 endpoint 식별값이 존재해야 한다.
    - 검증 실패 시 저장을 차단하고 해당 항목을 화면 2에서 강조한다.
4. **Bundle 자체 메타 자동 부여**
    - 시스템이 Bundle 메타데이터를 자동 생성한다.
    - `bundle_id`: UUID 생성
    - `bundle_version`: 첫 저장이면 `v1`, 갱신이면 `v2`, `v3` 등으로 증가
    - `active_period_start`: 계약 기간 시작일 참조
    - `active_period_end`: 계약 기간 종료일 참조
    - `created_at`: 현재 시각
    - `updated_at`: 현재 시각
    - `upload_session_id`: FR-iac-001에서 생성된 업로드 세션 ID 참조
5. **SLA Bundle 객체 조립**
    - 시스템이 `SLABundleDraft`를 최종 SLA Bundle 객체로 변환한다.
    - SLA Bundle은 다음 구조를 포함한다.

- 활성 필드는 최종 Bundle 값으로 저장한다.
- 비활성 필드는 `activation_status=inactive`, `review_status=not_applicable`로 저장한다.
- LLM 추천값은 운영자 승인 여부와 함께 저장한다.
- 운영자 수정값은 최종값으로 저장하며, 원래 LLM 추천값은 감사 추적용 메타데이터로 보존한다.
1. **DB 영구 저장**
    - 시스템은 SLA Bundle을 DB에 영구 저장한다.
    - PostgreSQL + JSONB 또는 동등한 문서형 저장 구조를 사용할 수 있다.
    - 저장은 단일 트랜잭션으로 처리하여 일부 저장 상태를 방지한다.
    - 저장 성공 후 `SLABundleDraft`는 archive 또는 삭제 처리한다.
    - 해당 고객사·서비스에 대해 active 상태의 SLA Bundle이 유일하게 존재하도록 관리한다.
2. **감사 로그 기록**
    - 시스템은 Bundle 저장 이력을 감사 로그에 기록한다.
    - 기록 대상:
        - 저장 시각
        - `bundle_id`
        - `bundle_version`
        - 운영자 ID
        - 확정 필드 수
        - `not_applicable` 필드 수
        - LLM 추천값 승인/수정/거부 이력
        - 최종 검증 결과
3. **저장 완료 알림 및 화면 3 진입**
    - 운영자에게 "SLA Bundle 저장 완료" 토스트 알림 표시
    - 시스템이 화면 3으로 라우팅
    - `bundle_id`를 화면 3 토폴로지 추천 단계의 입력 파라미터로 전달
    - 해당 고객사·서비스의 service status를 `구축중` 상태로 전환

**예외 흐름**

- ① **DB 저장 실패**
    - 트랜잭션을 롤백한다.
    - 운영자에게 "저장 실패 — 잠시 후 다시 시도해주세요." 오류 알림을 표시한다.
    - `SLABundleDraft` 상태는 유지한다.
    - "확인" 버튼을 재활성화하여 재시도 가능하게 한다.
- ② **활성 필수 필드 누락 감지**
    - 최종 검증에서 활성 필수 필드 누락이 발견되면 저장을 차단한다.
    - 화면 2로 복귀하고 해당 필드를 시각적으로 강조한다.
    - 챗봇 modal에 명확화 필요 알림을 표시한다.
- ③ **P0 명확화 질문 미해결**
    - P0 질문이 남아 있으면 저장을 차단한다.
    - 챗봇 modal을 자동 펼침 처리하고 남은 질문을 표시한다.
- ④ **SLA-인프라 정합 위반 잔존**
    - 정합성 위반이 잔존하면 저장을 차단한다.
    - 운영자에게 "SLA 정합 위반이 미해결입니다. 챗봇 또는 Form 수정으로 해결 후 다시 시도하세요." 메시지를 표시한다.
    - 관련 필드를 화면 2에서 강조한다.
- ⑤ **비활성 필드가 후속 단계 필수값으로 필요한 경우**
    - 예: RPO가 활성인데 backup 관련 필드가 `not_applicable`로 처리된 경우
    - 시스템은 저장을 차단하고 해당 필드의 활성화 상태 재검토를 요구한다.
    - FR-iac-004 챗봇 명확화 질문으로 라우팅한다.
- ⑥ **동시 수정 충돌**
    - 여러 탭 또는 세션에서 동일한 `SLABundleDraft`를 수정한 경우 충돌을 감지한다.
    - 운영자에게 "다른 세션에서 변경되었습니다. 새로고침 후 다시 시도하세요." 메시지를 표시한다.
    - 마지막 유효 확인 액션만 처리한다.
- ⑦ **bundle_id 생성 충돌**
    - UUID 충돌 발생 시 시스템이 자동으로 새 UUID를 생성해 재시도한다.
    - 운영자에게는 별도 노출하지 않는다.
- ⑧ **Schema 변환 실패**
    - `SLABundleDraft`를 최종 SLA Bundle Schema로 변환할 수 없는 경우 저장을 차단한다.
    - 실패 필드와 원인을 시스템 로그 및 운영자 화면에 표시한다.

**사후 조건**

- SLA Bundle이 DB에 영구 저장된다.
- SLA Bundle은 active 상태가 된다.

- `bundle_id`가 부여된다.
- 저장된 Bundle은 화면 3 토폴로지 추천, 화면 4 Terraform 코드 생성, SLA 기반 모니터링 정책 생성의 단일 진실 공급원으로 참조된다.
- 비활성 필드는 `not_applicable` 상태로 저장되며 후속 단계의 기본 입력에서 제외된다.
- `SLABundleDraft`는 archive 또는 삭제 처리된다.
- 저장 이력과 운영자 승인 이력은 감사 로그에 보존된다.
- 화면 3 진입 트리거가 활성화되고 `bundle_id`가 입력 파라미터로 전달된다.
- 운영자에게 저장 완료 알림이 표시된다.
- 해당 고객사·서비스의 service status가 `구축중` 상태로 전환된다.
